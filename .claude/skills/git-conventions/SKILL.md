# Правила Git

Полные правила для людей — `CONTRIBUTING.md`. Здесь то, что Claude делает сам.

## Главное: предлагать, а не делать без спроса

- Коммит, push, создание PR, удаление веток — **только по просьбе пользователя**. Push с этой машины всё равно не пройдёт: у оболочки нет учётных данных GitHub, пушит пользователь.
- Но **предлагать готовые имена и сообщения нужно всегда**, не дожидаясь вопроса:
  - получив новую задачу на ветке `main` или на ветке другой задачи — предложить имя новой ветки и команду её создания;
  - закончив изменения — предложить сообщение коммита (или разбивку на несколько коммитов) и заголовок с описанием PR.
- Формат предложения в конце ответа:
  ```
  Ветка:  feature/comment-attachments
  Коммит: feat(upload): add image and TXT attachments to comments
  ```
  Если изменения логически разные — предложить несколько коммитов и какие файлы в какой (`git add <файлы>`).

## Ветки

`<тип>/<kebab-case-описание>`, от свежего `origin/main`:

| Тип | Когда |
|---|---|
| `feature/` | новая функциональность |
| `fix/` | исправление ошибки |
| `refactor/` | без изменения поведения |
| `docs/` | только документация (README, docs/, skills) |
| `test/` | только тесты |
| `ci/` | `.github/`, PHPStan, сборка |
| `chore/` | зависимости, конфиги, Docker |

Создание ветки — **без связи с `main`**, иначе `git push` уйдёт в `main`:

```bash
git fetch origin
git checkout -b <ветка> origin/main
git branch --unset-upstream          # checkout от origin/main ставит upstream = main
# первый push: git push -u origin <ветка>
```

Если текущая задача не совпадает с названием текущей ветки — сказать об этом и предложить новую ветку, а не дописывать в чужую (пример ошибки из истории: Elasticsearch закоммичен прямо в `main`, хотя ветка `add_elasticsearch` уже была).

## Сообщения коммитов

```
<type>(<scope>): <imperative summary, English, ≤ 72 chars, no period>

<body: why, if not obvious>
```

- type: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `ci`, `chore`, `style`.
- scope (по затронутой части): `api`, `search`, `upload`, `ws`, `queue`, `cache`, `security`, `frontend`, `form`, `docker`, `readme`, `wiki`, `skills`. Изменения во многих частях — scope не указывать.
- Ломающее изменение API (`api-conventions`, правило 1): `feat(api)!:` и `BREAKING CHANGE:` в теле.
- Один коммит = одно логическое изменение, после которого проходят pint, PHPStan и тесты. Тест вместе с кодом, который он проверяет, — в одном коммите.
- Нельзя: `fix`, `update`, `wip`, `README file edit`, две задачи через «and».

Подбор типа по файлам: только `*.md`/`docs/`/`.claude/skills/` → `docs`; только `tests/` → `test`; только `.github/`/`phpstan.neon` → `ci`; `composer.*`/`package*.json`/`docker/` без кода → `chore`.

## Перед push и PR

1. Проверки как в CI (команды в `CONTRIBUTING.md`, раздел «Pull request»).
2. `git fetch origin && git merge origin/main` — если `main` ушёл вперёд, конфликт разрешается локально. При конфликте: показать, что поменяла каждая сторона (`git diff <merge-base> origin/main -- <file>` и то же для ветки), объединить, проверить, оставить коммит слияния пользователю.
3. Заголовок PR — в формате коммита; описание: что сделано, как проверить.

## После слияния PR

```bash
git checkout main && git pull
git branch -d <ветка>      # -d, не -D: не даст удалить несмёрженное
```

`main` не переписывать (`push --force`, `rebase` опубликованных коммитов) — никогда. В своей ветке до слияния — можно (`--fixup` + `rebase --autosquash`).
